# GitHub 하네스

## 브랜치 전략

- 전략: Git-Flow
- `main`: 배포 가능한 안정 버전
- `develop`: 개발 통합 브랜치
- `feature/*`: 기능 개발
- `fix/*`: 일반 버그 수정
- `hotfix/*`: 긴급 수정
- `refactor/*`: 구조 개선
- `test/*`: 테스트 작업
- `docs/*`: 문서 작업
- `release/*`: 출시 준비

## 커밋 메시지 규칙

- 커밋 메시지는 한글로 작성한다.
- 기본 형식: `타입: 한글 설명 #이슈번호`
- 이슈 번호가 없으면 `#이슈번호`는 생략한다.
- 예시:
  - `feat: 플레이어 반동 추가 #124`
  - `fix: 낙사 판정 오류 수정 #208`
  - `docs: 하네스 문서 정리 #301`

## 커밋 타입

- `feat`: 새로운 기능 추가
- `fix`: 버그 수정
- `docs`: 문서 수정
- `test`: 테스트 코드 또는 테스트 작업
- `refactor`: 리팩토링
- `build`: 빌드 파일 수정
- `rename`: 파일 또는 폴더 이름만 수정한 경우
- `remove`: 파일 삭제만 수행한 경우

## 이슈 규칙

- 이슈 제목은 대괄호 타입으로 시작한다.
- 타입 첫 글자는 대문자로 작성한다.
- 예시:
  - `[Feat] 플레이어 반동 추가`
  - `[Fix] 낙사 판정 오류 수정`
  - `[Docs] 하네스 문서 보강`

## PR 규칙

- PR 제목은 `[Type] 작업 설명` 형식으로 작성한다.
- 대괄호 안 타입은 첫 글자를 대문자로 작성한다.
- 예시:
  - `[Feature] UI 제작`
  - `[Fix] 낙사 판정 오류 수정`
  - `[Docs] 작업 지시 가이드 추가`
- PR 본문은 항상 아래 3개 섹션으로 작성한다.
  - `## 개요`
  - `## 변경한 내용`
  - `## 기타 사항`
- `개요`에는 PR의 목적과 범위를 짧게 적는다.
- `변경한 내용`에는 실제 변경 사항을 목록으로 적는다.
- `기타 사항`에는 검증 결과, 미검증 항목, 리뷰어가 알아야 할 내용을 적는다.

## 작업 흐름

1. `develop`에서 작업 브랜치를 만든다.
2. 기능 단위로 작은 커밋을 남긴다.
3. 이슈 번호를 커밋 메시지에 연결한다.
4. 검증 후 `develop`으로 병합한다.
5. 출시 시점에 `release/*`를 거쳐 `main`으로 반영한다.

## DUOX 작업 분류 기준

- 캐릭터, 공격, 넉백, 낙사, 유령 시스템 변경은 기능 또는 밸런스 변경으로 분리한다.
- UI 선택 화면, 맵 선택, 옵션 화면 변경은 UI 작업으로 분리한다.
- 픽셀아트, 스프라이트, Aseprite 산출물 변경은 아트 작업으로 분리한다.
- 씬과 프리팹 변경은 연결 참조가 깨지지 않았는지 확인한 뒤 커밋한다.
- `WORK_ORDER.md`에 실제 작업 지시가 적혀 있었다면 작업 완료 후 템플릿 내용을 비운 상태로 커밋한다.
- 이때 `WORK_ORDER.md`의 `작업 이름`, `상세 요구사항`, `유저 메모장` 섹션에는 GitHub 업로드용 주석만 남긴다.
- `FILE_CHANGE_LOG.md`의 현재 작업 기록은 커밋 전 최신 상태로 정리한다.
- 커밋 직전 `FILE_CHANGE_LOG.md`의 `현재 커밋 안 된 작업` 섹션에서는 실제 작업 목록만 비우고 GitHub 업로드용 주석은 남긴다.
