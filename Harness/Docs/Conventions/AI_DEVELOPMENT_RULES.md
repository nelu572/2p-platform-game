# AI 개발 규칙

## 작업 우선순위

1. 현재 대화의 직접 프롬프트
2. `Harness/WORK_ORDER.md`
3. 하네스 문서와 프로젝트 구조

충돌이 있으면 더 높은 우선순위를 따른다. 확실하지 않은 프로젝트 고유 정보는 `확인 필요`로 남긴다.

## 작업 원칙

- 프롬프트, 지시서 등을 확인하고 보고서를 작성하여 한번 묻고 작업한다.
- 작업 시작 전 관련 파일을 먼저 읽고 현재 구조를 확인한다.
- 기획 관련 작업은 `Harness/Docs/Planning/PROJECT_PLAN.md`를 먼저 확인한다.
- Unity 씬, 프리팹, ScriptableObject, 메타 파일의 연결 관계를 고려한다.
- 기존 public API, 기존 시스템, 책임 경계를 불필요하게 흔들지 않는다.
- 사용자 변경으로 보이는 파일은 임의로 되돌리지 않는다.
- 변경 범위는 요청된 작업과 직접 관련된 파일로 제한한다.
- DUOX의 핵심 구조인 로컬 2인 PVP, 캐릭터 선택, 맵 선택, 낙사, 넉백, 유령 개입 흐름을 임의로 약화하지 않는다.

## 구현 원칙

- C# 스크립트는 Unity 생명주기와 기존 컴포넌트 구조에 맞춘다.
- 인스펙터에서 연결된 필드, 프리팹 참조, 씬 오브젝트 이름을 임의로 변경하지 않는다.
- 반복 로직은 필요할 때만 공통화하고, 단순한 작업에 과한 추상화를 만들지 않는다.
- 새 에셋이나 스크립트를 만들 때는 프로젝트의 기존 폴더 구조를 따른다.
- 외부 패키지 추가가 필요하면 먼저 이유와 영향을 확인한다.
- 플레이어 입력, 사망 판정, 넉백, 낙사, 유령 상태 전환은 전투 밸런스에 직접 영향을 주므로 관련 파일과 씬 참조를 함께 확인한다.
- 캐릭터별 공격 방식은 공통 인터페이스와 개별 구현의 책임을 분리한다.
- Input System 액션, 씬 전환, UI 선택 그룹을 바꿀 때는 P1 / P2 양쪽 흐름을 함께 확인한다.
- URP, UGUI, DOTween 사용 흔적이 있으므로 기존 연출/렌더링 방식을 먼저 따른다.

## 작업 기록 규칙

- 작업 후 `Harness/Docs/Logs/FILE_CHANGE_LOG.md`에 변경 요약을 남긴다.
- 로그는 `현재 커밋 안 된 작업`과 날짜별 섹션으로 나누어 작성한다.
- 날짜별 로그에는 변경 파일, 변경 목적, 검증 결과를 간단히 적는다.
- 가능한 검증을 수행한다. 검증하지 못한 경우 이유를 기록한다.
